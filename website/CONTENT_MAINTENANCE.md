# Content maintenance

1. Check the parent authoritative scope/status/license; never change product policy by editing a teaching page alone.
2. Add a permanently named Markdown file to the appropriate src/content collection. Follow an existing article's frontmatter and required schema. Keep descriptions useful and within40–180characters. Put relative site paths in related; leading-root links in Markdown are adapted by the base-aware presentation plugin.
3. Experiment articles need objectives, prerequisites, explanation, domain-qualified equations/units, actual workflow, genuine image, conceptual diagram, interpretation, pitfalls, FAQ, related reading and references. Use an independent example only when labelled as such.
4. Write literal `\omega` for angular frequency and `\Omega` for ohms. In GFM tables use `\lvert V\rvert`, not raw vertical bars that split cells. KaTeX is strict/trust=false. Inspect rendered MathML/Greek glyphs and tables after build.
5. Check complex-Zc voltage-versus-power, classical lossless VSWR and constant-parameter Heaviside assumptions. Do not add transient/FMI/branched-network features by implication. Current-only exports are not recording/history.
6. Update release facts only in the validated manifest and actual authoritative root docs, with separately approved source changes/hashes. FAQ release placeholders derive from that manifest. Never auto-fetch latest releases at build time.
7. Run check, scientific/contract tests, build and validate. Retest affected pages with keyboard/themes/mobile layouts. Keep facts and evidence dates current.

Changing an approved root policy requires deliberate review and updating its verified snapshot record. Root license bytes must never be normalized/reworded accidentally. Render presentation may adapt headings/known links without becoming a second policy authority.
